## Corrected contract
- Firebase Authentication **remains the authority** for account credentials, verification, reset codes and expiry. Gmail SMTP is a delivery transport only.
- The API now sends NEW Firebase Admin verification/reset emails containing an HTTPS Android-verified app link: `https://oil-spill-monitoring-buoy.firebaseapp.com/open/auth-action?mode=resetPassword|verifyEmail&oobCode=<firebase-issued-single-use-code>&apiKey=<public-project-key>`.
- API validates original Firebase Admin-generated `/__/auth/action` link: HTTPS exact host, mode, one code/key each, correct project key, no unexpected redirect. It copies only `mode`, `oobCode`, `apiKey` to the trusted Android App Link.
- The installed BlueGuard APK is the **only client** which completes new actions. Android MainActivity receives the verified HTTPS URL with explicit path `/open/auth-action`; Angular accepts only the exact expected Firebase host, path and three unique parameters, verifies the public Firebase project key and action mode, deletes the raw URL from WebView sessionStorage, and holds the one-time code **in memory only**. The Angular route `/email-action` never contains `oobCode`, email or password.
- The new Ionic email-action screen uses Firebase JS `verifyPasswordResetCode` then `confirmPasswordReset` and requires password confirmation. It never asks for the old password. On success it clears the code, signs out any existing Firebase local session, and directs the user to Login with the new password. Invalid/expired/replayed codes are rejected by Firebase; no account or buoy role is granted from a URL.
- Email verification also completes inside the app (`checkActionCode` + `applyActionCode`), without trusting a return URL as proof. If the active signed-in account differs from the code's verified address, it cannot be silently granted account access. Firebase Auth and API bootstrap retain their separate access checks.
- Old `/auth/action` browser links continue to work if they were emailed **before the change**; **new** native links do not require Hosting action handler or a Firebase Console Templates setting. A new email is required to test the new native path.
- The web fallback `/open/auth-action` does NOT process codes; it removes them from address history and instructs the user to open the installed Android app. No automatic website password-reset form.

## Limitations and security
App-only action links REQUIRE the updated Android app and a working Android-verified Firebase Hosting domain association. Some Android mail/browser link settings can prevent App Link handoff; check `Open supported links`, package association and installed signing certificate. The action code is a bearer secret present in the *email URL* (as in Firebase's normal browser link), but is never sent through API logs, app router paths, analytics or stored permanently by BlueGuard. Scrub screenshots and recordings. Avoid sending unrelated action codes to third-party URL shorteners.
Existing Resend sender remains available as a transport, but has no role in action completion. Neither Firebase default templates nor the previous Hosting `/auth/action` web handler should be used for NEW SMTP-generated app-only links.
